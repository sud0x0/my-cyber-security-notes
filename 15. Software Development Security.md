# Software Development Security

---

## Overview

_Volatile facts (framework versions, requirement numbers, reporting clocks) are maintained in [note 00](00.%20Current%20Versions%20and%20Facts.md). Check it before relying on figures here._

Software development security is the discipline of embedding security practices throughout the entire software development life cycle (SDLC) — from requirements through design, coding, testing, deployment, and maintenance. The goal is to prevent vulnerabilities from entering software in the first place, rather than finding and fixing them after the fact.

It sits at the intersection of engineering and security, and overlaps heavily with DevSecOps, which operationalises these practices inside automated pipelines. Where DevSecOps is primarily about tooling and velocity, software development security is the broader discipline that includes governance, secure design, code quality, and vulnerability management across any development methodology — Waterfall, Agile, or otherwise.

In the Australian context, this domain intersects with several mandatory and quasi-mandatory frameworks. The **Protective Security Policy Framework (PSPF) Release 2025** (published July 2025) places software security within its Technology Security domain, requiring Commonwealth entities to manage the security lifecycle of their information and operational technology systems. The **ASD Information Security Manual (ISM)**, updated quarterly (verify the current release at cyber.gov.au), contains a dedicated chapter of controls for software development that applies to all government systems and, in practice, to contractors and suppliers handling government data. The **Security of Critical Infrastructure Act 2018 (SOCI Act)**, as amended by the Enhanced Response and Prevention Act 2024 (in force December 2024), requires responsible entities across 11 critical sectors to manage software and supply chain vulnerabilities as part of their Critical Infrastructure Risk Management Programme (CIRMP). The **Cyber Security Act 2024** (Royal Assent November 2024) introduces mandatory minimum security standards for connectable devices and mandatory ransomware payment reporting — both with direct implications for how software is built and maintained.

Software development security is also addressed by ISC2's CISSP (Domain 8) and CSSLP certifications, ISACA's CISM and CISA bodies of knowledge, NIST SP 800-218 (SSDF), the OWASP suite of projects, and ISO/IEC 27002:2022 (controls 8.25–8.34).

## Why It Matters

Software is the dominant attack surface in modern organisations. The consequences of poor development security are direct and severe.

**Equifax (2017):** A known, unpatched vulnerability in Apache Struts allowed attackers to exfiltrate personal data on 147 million people. The patch had been available for months before exploitation. The failure was process and governance, not a zero-day.

**SolarWinds (2020):** Attackers compromised the software build pipeline, injecting malicious code into signed, legitimate software updates distributed to 18,000+ organisations. No application-level vulnerability was needed — the development process itself was the attack vector. This incident directly shaped the ISM's controls protecting the authoritative source for software (ISM-1422, ISM-1816) and SBOM requirements (ISM-1730).

**Log4Shell (2021):** A remote code execution vulnerability in the Log4j logging library affected millions of applications globally. Organisations without a software bill of materials had no rapid way to determine their exposure.

**Medibank (2022):** Personal data on nearly 10 million Australians was exfiltrated. The incident resulted in targeted government sanctions and reinforced that application and data system vulnerabilities are treated as a national security concern under the SOCI Act — not merely a compliance matter.

Defects found in production cost exponentially more to remediate than those found during design. Security debt compounds across every release cycle.

## Core Concepts

**Security must be designed in, not bolted on.** Security requirements belong in the same backlog as functional requirements. If a system is designed without authentication boundaries, no amount of testing will fix the architectural gap — it just reveals it too late. OWASP Top 10:2021 (A04 — Insecure Design) explicitly recognises that design flaws are distinct from implementation bugs. The ASD ISM mandates threat modelling as part of application development (ISM-1238).

**The SDLC as a security control.** Every phase of development offers an opportunity to reduce risk. Requirements gathering surfaces misuse cases. Architecture review exposes trust boundary problems. Code review catches implementation errors. Testing validates security controls and their absence. Deployment configuration determines the runtime attack surface.

**Shift left.** Finding and fixing a vulnerability during design costs a fraction of finding it in production. Shift left means moving security activities as early as possible — threat modelling at architecture stage, static analysis in the developer's IDE, dependency scanning in the build pipeline.

**Secure by design and secure by default.** The ASD ISM (ISM-0401) mandates use of secure-by-design and secure-by-default principles, memory-safe programming languages (C#, Go, Java, Ruby, Rust, Swift), and secure programming practices as part of application development. PSPF 2025 embeds zero trust principles across the Technology Security domain — applications must be designed on the assumption that network trust cannot be presumed.

**Software supply chain security.** Modern software is mostly composed, not written. A typical enterprise application depends on hundreds of third-party packages. Each dependency is a trust decision. The 2024 SOCI Act amendments explicitly brought data storage systems holding operational data — including source code, encryption keys, algorithms, and network blueprints — within the scope of critical infrastructure asset definitions, making supply chain integrity a legislative obligation for regulated entities. OWASP Top 10:2025 RC elevates software supply chain failures to a dedicated top-three category.

**Software bill of materials (SBOM).** ISM-1730 requires that an SBOM be produced and made available to consumers of software. A cryptographic bill of materials (CBOM) extends this to document cryptographic dependencies and algorithm implementations — directly relevant to PSPF 2025's new post-quantum encryption guidance.

**Threat modelling.** Formal analysis of how an adversary could attack a system, conducted before or during design. Common methods include:

```
STRIDE          PASTA           LINDDUN
-----------     -----------     -----------
Spoofing        7-stage risk-   Privacy-focused
Tampering       centric model   (linkability,
Repudiation     Connects biz    detectability,
Info disclose   objectives to   disclosure,
Denial of svc   technical       non-compliance)
Elevation priv  requirements
```

VAST and Attack Trees are also in common use. LINDDUN is particularly relevant when designing systems processing personal information subject to the Australian Privacy Act 1988.

**Protecting the authoritative source for software.** The ISM requires: development, testing, and production environments to be segregated (ISM-0400); software development to occur only in development environments (ISM-1419); production data not to be used in development or test unless secured to the same level (ISM-1420); unauthorised access to and modification of source repositories to be prevented (ISM-1422, ISM-1816); and all changes to be linked to documented decisions in an issue tracking system (ISM-2025).

**Vulnerability disclosure.** The ISM requires a vulnerability disclosure programme (ISM-1616), a formal policy (ISM-1755), documented procedures (ISM-1756), a `security.txt` file on each internet-facing domain (ISM-1717), and root cause analysis for resolved vulnerabilities (ISM-1909). ASD operates as an independent coordinator for coordinated vulnerability disclosure.

**ACID and data integrity.** Database operations in applications should preserve Atomicity, Consistency, Isolation, and Durability. Failures here underpin many injection and business logic vulnerabilities. Application-layer input controls — limit checks, sequence checks, checksums, check digits — reduce the attack surface for data manipulation.

## How It Works in Practice

**Roles**

- **Security champions** — developers embedded in product teams with security training, serving as the first line of review.
- **Application security engineers** — own tooling, standards, threat modelling templates, and triage processes.
- **Architects** — responsible for secure design patterns and documented trust boundaries.
- **IRAP assessors** — for government systems, required for assessing outsourced and cloud services under PSPF/ISM. Cannot be substituted by entity assessors for these system types.
- **Authorising officer** — typically the CISO or delegate, formally accepts residual security risk and issues authorisation to operate (ATO). Required for every government system.

**Security activities mapped to SDLC phase:**

```
Phase           Security Activity
-----------     -----------------------------------------------
Requirements    Security requirements, abuse/misuse cases,
                PSPF classification and handling needs,
                Privacy Act obligations, SOCI CIRMP scope
                check, regulatory mapping

Design          Threat modelling (STRIDE/PASTA/LINDDUN),
                data flow diagrams, trust boundary review,
                ISM control selection, zero trust design,
                LINDDUN for personal information systems

Implementation  Secure-by-design / secure-by-default (ISM-0401),
                memory-safe language use, peer code review,
                SAST, SCA / dependency scanning, secrets
                detection, digital signing of executables
                (ISM-1796), issue tracking linkage (ISM-2025)

Testing         DAST, penetration testing, fuzz testing,
                OWASP ASVS verification (ISM-0971), OWASP
                Top 10 mitigation check (ISM-1850), security
                regression tests

Deployment      Environment segregation enforcement (ISM-0400),
                no production data in dev/test (ISM-1420),
                secrets management, least privilege for
                service accounts, SBOM + CBOM generation
                (ISM-1730), system authorisation (ATO)

Maintenance     Vulnerability disclosure programme (ISM-1616,
                1755, 1756, 1717), CVE/dependency monitoring,
                root cause analysis (ISM-1909), patch mgmt,
                periodic penetration testing, CIRMP review,
                ransomware response plan (72-hour reporting
                under Cyber Security Act 2024)
```

**Tooling categories**

- **SAST (Static Application Security Testing):** Analyses source code without execution. Catches injection patterns, hardcoded secrets, unsafe function use. Tools: Semgrep, Checkmarx, SonarQube, Veracode.
- **DAST (Dynamic Application Security Testing):** Tests running applications. Catches runtime behaviour issues, misconfiguration, authentication failures. Tools: OWASP ZAP, Burp Suite, Invicti.
- **IAST (Interactive AST):** Agent-based, runs during functional testing.
- **SCA (Software Composition Analysis):** Identifies known vulnerabilities in third-party dependencies. Tools: Dependabot, Snyk, OWASP Dependency-Check, Black Duck.
- **Secrets scanning:** Detects credentials committed to source control. Tools: Trufflehog, Gitleaks, GitHub Advanced Security.

**Australian Government system authorisation.** Software systems must go through formal assessment and authorisation before operating in production. The system owner obtains ATO from the authorising officer (CISO or delegate) based on accepted residual security risk. This requires a System Security Plan (SSP) documenting the software development approach against ISM controls. ASD's Blueprint for Secure Cloud provides SSP templates for cloud-hosted systems.

## Common Mistakes and Weaknesses

**Security requirements treated as optional.** Product backlogs contain functional stories and no security stories. Under PSPF and SOCI, this is a governance failure with compliance consequences, not merely a technical gap.

**Threat modelling skipped.** ISM-1238 mandates threat modelling. Teams that skip it consistently recreate the same vulnerability classes — broken access control, insecure direct object references, missing authentication on sensitive functions.

**No SBOM.** ISM-1730 mandates SBOM production. Organisations without it cannot rapidly triage exposure to new CVEs, cannot meet CIRMP supply chain hazard requirements, and cannot support procurement due diligence from downstream government customers.

**No vulnerability disclosure programme.** ISM requires a formal programme, policy, procedures, and `security.txt`. Many organisations have none of these. A researcher who finds a vulnerability and cannot find a responsible disclosure channel will either go public or sell it.

**Production data in development environments.** ISM-1420 prohibits this unless the development environment is secured to the same level as production. This control is frequently violated. It also creates unnecessary personal information exposure under the Privacy Act 1988.

**SAST as a checkbox.** SAST tools generate findings that are ignored or suppressed without review. The failure is process — SAST requires triage policies, false positive management, and governance requiring remediation within defined timeframes.

**No environment segregation.** ISM-0400 requires development, testing, and production environments to be segregated. ISM-1419 requires software development to occur only in development environments. Violations are common under delivery pressure.

**Hardcoded credentials.** Despite wide tooling availability, secrets committed to source control remain a high-frequency finding. Culture and process failure.

**SOCI scope not assessed for development systems.** The 2024 SOCI amendments bring data storage systems holding operational data — source code, encryption keys, algorithms, network blueprints — within the potential definition of a critical infrastructure asset. Responsible entities that have not assessed whether their development and build systems fall within CIRMP scope likely have unidentified obligations.

**Ransomware response not integrated into software operations.** The Cyber Security Act 2024 requires ransomware payment reporting within 72 hours. If development and operations teams do not have incident response processes connected to this obligation, the window will be missed.

## Connections to Other Domains

- **[Cyber Governance and Management (1)](01.%20Cyber%20Governance%20and%20Management.md):** Security development standards must be mandated from governance level. Under PSPF 2025, CISOs have increased accountability and more frequent reporting obligations. The ATO process is a formal governance gate — the authorising officer accepts residual risk, which must include software security risk.

- **[Cyber Risk Management (2)](02.%20Cyber%20Risk%20Management.md):** Risk appetite informs testing depth and threat model priorities. SOCI CIRMP requires that cyber risks — including software vulnerability exploitation and supply chain compromise — be formally identified and managed. CIRMP must be reviewed annually and after material changes.

- **[Legal, Regulatory, and Compliance (3)](03.%20Legal,%20Regulatory,%20and%20Compliance.md):** The Privacy Act 1988 imposes obligations on how personal data is handled within applications. SOCI creates sector-specific mandatory requirements. The Cyber Security Act 2024 creates new obligations for device manufacturers and ransomware-affected businesses. These must be translated into security requirements at the start of the SDLC, not bolted on at the end.

- **[Privacy and Data Protection (4)](04.%20Privacy%20and%20Data%20Protection.md):** The Australian Privacy Principles (APPs) require personal information to be protected by reasonable security measures — beginning at design. LINDDUN threat modelling is directly applicable. ISM-1420 prohibits production personal data in development environments without equivalent security controls.

- **[Vendor Management (5)](05.%20Vendor%20Management.md):** Third-party software, open source libraries, and outsourced development all introduce supply chain risk. PSPF 2025 introduces expanded FOCI risk requirements in procurement. SOCI entities must assess data storage and processing vendors against CIRMP obligations. SBOMs are a procurement tool as much as a development one.

- **[Asset and Change Management (6)](06.%20Asset%20and%20Change%20Management.md):** Software components are assets. PSPF 2025 requires a stocktake of all internet-facing systems. ISM-2025 requires all development changes to be linked to documented decisions in issue tracking. Change management prevents unreviewed code from reaching production.

- **[Identity and Access Management (8)](08.%20Identity%20and%20Access%20Management.md):** Broken access control (OWASP Top 10:2021 A01) is the most prevalent web application vulnerability class. It is an IAM failure at the application layer. Authentication and authorisation must be designed against ISM authentication hardening guidance and OWASP ASVS requirements.

- **[Cryptography (9)](09.%20Cryptography.md):** Cryptographic failures (OWASP Top 10:2021 A02) arise when developers implement cryptography incorrectly. ISM-1730 requires a CBOM. PSPF 2025 introduces post-quantum encryption guidance — software implementing cryptography must support algorithm agility to enable transition.

- **[Cyber Testing (10)](10.%20Cyber%20Testing.md):** Penetration testing, DAST, fuzzing, and security code review are forms of security testing on software. OWASP ASVS provides structured test scope. For government systems, IRAP assessors perform formal security assessments. CIRMP requires responsible entities to conduct regular vulnerability assessments.

- **[Threat Intelligence (11)](11.%20Threat%20Intelligence.md):** Threat intelligence informs which vulnerability classes are being actively exploited and which dependencies have new CVEs. SOCI entities subject to Enhanced Cyber Security Obligations (ECSO) for Systems of National Significance must participate in national cyber exercises — intelligence from those exercises should inform development security priorities.

- **[Security Operations and Monitoring (12)](12.%20Security%20Operations%20and%20Monitoring.md):** Applications must produce security-relevant logs. ISM-1911 requires that web application crashes and error messages be centrally logged. Logging and monitoring failures (OWASP Top 10:2021 A09) are design-time decisions that cannot be cost-effectively retrofitted.

- **[Incident Management and Business Continuity Planning (13)](13.%20Incident%20Management%20and%20Business%20Continuity%20Planning.md):** The Cyber Security Act 2024 requires ransomware payment reporting within 72 hours — requiring incident response processes that begin at first awareness. Vulnerability disclosure processes (ISM-1616) and patch response processes are extensions of incident management. Software must be designed to be patchable.

- **[Cloud Management (14)](14.%20Cloud%20Management.md):** Cloud-native applications introduce misconfiguration risk (OWASP Top 10:2021 A05). PSPF 2025 requires IRAP-assessed cloud providers and PDNS for government systems. Infrastructure as code must be treated with the same security review rigour as application code.

- **[DevOps and DevSecOps (16)](16.%20DevOps%20and%20DevSecOps.md):** DevSecOps operationalises software development security inside CI/CD pipelines. ISM-1780 references SecDevOps practices for application development. ISM-1796 requires digital signing of executable files as part of development — a control that must be implemented in the pipeline.

- **[Cyber Architecture (17)](17.%20Cyber%20Architecture.md):** Secure design principles — least privilege, defence in depth, fail secure, separation of duties, zero trust — originate in architecture and must be applied at the application layer. PSPF 2025's zero trust mandate applies to how applications authenticate and authorise, not just network controls.

- **[Cyber Culture and Education (18)](18.%20Cyber%20Culture%20and%20Education.md):** Developer security training is the highest-ROI investment in application security. PSPF 2025 requires security awareness as part of its personnel and technology security domains. Developers who understand OWASP Top 10 write fewer of those vulnerabilities.

- **[LLM Security (19)](19.%20LLM%20Security.md):** AI-generated code frequently contains known vulnerability patterns. ISM-2094 (December 2025) mandates content filtering in AI applications to detect and block sensitive data exposure and improper output. NIST SP 800-218A extends the SSDF to AI model development. Code review processes must account for AI-generated code as a new source of introduced weaknesses.

- **[Physical Security (20)](20.%20Physical%20Security.md):** Physical access to development workstations, build servers, and source repositories is a security control. A physically compromised build server is a supply chain attack. ISM environment segregation requirements have physical as well as logical dimensions.
