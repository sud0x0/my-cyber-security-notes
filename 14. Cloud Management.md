# Cloud Management

---

## Overview

_Volatile facts (framework versions, requirement numbers, reporting clocks) are maintained in [note 00](00.%20Current%20Versions%20and%20Facts.md). Check it before relying on figures here._

Cloud management is the discipline of governing, securing, and operating an organisation's use of cloud computing services across their full lifecycle — from procurement and onboarding through to configuration, monitoring, and exit. It sits at the intersection of IT operations, security, risk, and compliance. NIST SP 800-145 (2011) defines cloud computing as on-demand network access to a shared pool of configurable resources that can be rapidly provisioned and released with minimal management effort. The model is characterised by five essential characteristics: on-demand self-service, broad network access, resource pooling, rapid elasticity, and measured service. These same characteristics — speed, abstraction, shared tenancy, and dynamism — are precisely what make cloud environments operationally powerful and security-complex.

Cloud management is distinct from cloud _security_ in the narrow sense. It encompasses the full governance layer: who is allowed to provision what, under what controls, in which environments, with what visibility, and with which exit rights. In the Australian context, cloud management is shaped by a layered compliance environment: the PSPF (for Commonwealth entities and their supply chains), the ISM (technical controls), IRAP assessments (independent assurance), the HCF (hosting sovereignty), and the SOCI Act (for critical infrastructure operators). Understanding which of these instruments applies — and where they interact — is a core cloud management competency for any practitioner operating in or supplying to Australian government or critical infrastructure sectors.

---

## Why It Matters

Cloud environments fail in predictable ways when there is no coherent management discipline. The consequences are concrete:

**Misconfiguration is the dominant failure mode.** The Cloud Security Alliance's Top Threats to Cloud Computing 2024 report listed misconfiguration and inadequate change control as the number one threat. Around 23% of cloud security incidents stem directly from misconfiguration (SentinelOne, 2024), with 82% of those attributable to human error. Gartner has consistently stated that through 2025, 99% of cloud security failures will be the customer's fault. Toyota exposed 260,000 customer records in 2023 because of a cloud misconfiguration. Detection time for a configuration issue averages over 180 days.

**The shared responsibility model is systematically misunderstood.** A cloud service provider (CSP) secures _of_ the cloud; the customer is responsible for security _in_ the cloud. The exact boundary shifts by service model — IaaS, PaaS, or SaaS — and organisations regularly assume the CSP has covered something that they have not. This is the root cause of exposed storage buckets, disabled logging, and absent encryption.

**Australian compliance obligations are more demanding than international baselines.** Commonwealth entities and their suppliers face mandatory PSPF and ISM requirements, IRAP assessment obligations for cloud systems, and HCF certification requirements for hosting providers. SOCI Act obligations layer on top for critical infrastructure operators. A cloud deployment that satisfies ISO 27001 or CSA STAR is not automatically PSPF-compliant.

**Multi-cloud compounds the problem.** Around 79–88% of organisations now operate across multiple cloud providers. Inconsistent controls, different native security tooling, separate identity stores, and fragmented visibility create policy gaps that neither provider is responsible for closing.

**Data sovereignty is a legal obligation, not a configuration preference.** Cloud workloads can land in jurisdictions that conflict with PSPF data handling requirements, Australian Privacy Act obligations, or SOCI Act protections without the organisation being aware. For OFFICIAL: Sensitive and PROTECTED data, residency in Australian data centres is a requirement, not a design option.

**Shadow IT is structural, not exceptional.** When employees can sign up for a SaaS product with a credit card in minutes, the organisation's security perimeter becomes irrelevant unless there are controls at the access layer. Shadow cloud is not a bad-behaviour problem; it is a governance design problem.

## Core Concepts

**The Shared Responsibility Model**

The most important concept in cloud security. The model divides security obligations between the CSP and the customer, and the boundary depends on the service model. In the Australian government context, the ISM's Cloud Controls Matrix (CCM) extends this concept by explicitly mapping which ISM controls can be inherited from the CSP and which must be implemented by the cloud consumer.

```
  RESPONSIBILITY SPLIT BY SERVICE MODEL

  Control Plane                IaaS      PaaS      SaaS
  -------------------------------------------------------
  Physical infrastructure      CSP       CSP       CSP
  Virtualisation / hypervisor  CSP       CSP       CSP
  OS and runtime               Customer  CSP       CSP
  Middleware / platform        Customer  CSP       CSP
  Application                  Customer  Customer  CSP
  Data classification          Customer  Customer  Customer
  Identity and access          Customer  Customer  Customer
  Encryption (data at rest)    Customer  Shared    Shared
  Network controls             Shared    Shared    CSP
  -------------------------------------------------------
  ISM control inheritance      Partial   Greater   Greater
  Customer residual controls   High      Medium    Lower
  -------------------------------------------------------
```

The customer's responsibilities never fully disappear, even in SaaS. Identity, data classification, and access management remain customer-owned regardless of the service model. IRAP assessors are required to document the shared responsibility model clearly in every cloud assessment report.

**Deployment Models**

NIST SP 800-145 defines four: public cloud (open use, managed by the CSP), private cloud (exclusive use, may be on- or off-premises), community cloud (shared by organisations with common concerns), and hybrid cloud (composition of two or more). The deployment model affects the threat surface, the regulatory posture, and the contractual leverage available to the customer. For Australian government entities, deployment model selection has direct PSPF and HCF implications — PROTECTED data must be hosted with a certified HCF provider.

**Cloud Governance**

Cloud governance is the set of policies, processes, and controls that determine how cloud services are selected, provisioned, used, and decommissioned. Without it, cloud sprawl occurs: shadow IT, abandoned instances, ungoverned data stores, and cost overruns. A cloud governance framework covers service approval, landing zone design (standardised, pre-approved environments), cost management, and compliance guardrails. Under the PSPF, entities must maintain a security risk management process covering procurement and outsourcing, which includes cloud service selection and ongoing management.

**Cloud Security Posture Management (CSPM)**

CSPM tooling continuously scans cloud environments for misconfigurations and policy violations against a defined baseline. It is the primary operational control for catching configuration drift — the accumulation of ad hoc changes that cause a once-compliant environment to silently diverge from its required state. CSPM is also the primary mechanism for demonstrating ongoing compliance with ISM controls that require continuous monitoring of cloud configurations.

**Cloud Workload Protection (CWPP) and CNAPP**

Cloud Workload Protection Platforms (CWPP) protect compute, containers, and serverless functions at runtime — scanning for vulnerabilities, detecting anomalous behaviour, and enforcing runtime policies. Cloud-Native Application Protection Platforms (CNAPP) converge CSPM and CWPP into a single control plane, addressing the practical need to manage posture and runtime protection together without maintaining separate tool sets.

**Cloud Access Security Broker (CASB)**

A CASB is a security policy enforcement point positioned between an organisation's users and the cloud services they access. Gartner coined the term in 2012 and defined CASBs around four pillars:

- **Visibility** — discovers what cloud services are being used, including unsanctioned shadow IT. Most organisations significantly underestimate their cloud service footprint until a CASB discovers it.
- **Compliance** — enforces data residency, access policy, and regulatory requirements for data in cloud services, regardless of whether the service is sanctioned.
- **Data security** — applies DLP policies to data moving to and from cloud services. Blocks sensitive data from being uploaded to personal accounts or unapproved services, and enforces encryption in transit.
- **Threat protection** — detects anomalous user behaviour, compromised accounts, and malware propagation through cloud storage.

CASBs operate in three deployment modes, often combined: API-mode (connects directly to SaaS apps via their APIs for deep inspection of data at rest), forward proxy (intercepts outbound traffic from managed devices in real time), and reverse proxy (intercepts traffic at the application layer regardless of device, important for BYOD environments). Under PSPF 2025, gateway security controls and Security Service Edge capabilities are now explicitly referenced as required controls for entities accessing cloud services.

Gartner ceased publishing a standalone CASB Magic Quadrant in 2020. CASB capability is now evaluated as part of Security Service Edge (SSE) platforms.

**Shadow IT and Unsanctioned Cloud**

Shadow IT in the cloud context refers to cloud services provisioned or used by employees without IT or security approval. Because cloud adoption requires no physical infrastructure and can be initiated with a credit card, shadow cloud is structurally inevitable unless controlled at the access layer. CASB is the primary technical control. For Commonwealth entities, the use of unsanctioned cloud services to store or process OFFICIAL: Sensitive or PROTECTED data is a PSPF breach — the obligation to manage information holdings proportionally to their sensitivity applies regardless of which platform that information ends up on.

**Infrastructure as Code (IaC) Security**

IaC is the practice of defining cloud infrastructure — compute, storage, networking, IAM policies — as machine-readable configuration files (Terraform, AWS CloudFormation, Azure Bicep, Kubernetes manifests, and others) that are version-controlled and deployed through automated pipelines. IaC provides repeatable, auditable, and scalable infrastructure provisioning.

The specific risk IaC introduces is propagation at scale: a misconfiguration in a template is replicated across every environment that template provisions. An overly permissive IAM policy written once in Terraform can be deployed into dozens of environments before anyone notices.

IaC security addresses this by scanning configuration files for misconfigurations, policy violations, hardcoded secrets, and overly permissive settings before deployment. This is integrated into CI/CD pipelines as a blocking gate. Policy-as-code (PaC) frameworks such as Open Policy Agent (OPA) allow organisations to express security requirements as machine-readable rules enforced automatically at pipeline time.

**Secrets Management**

Cloud environments regularly accumulate exposed credentials: API keys hardcoded in IaC templates, long-lived access keys attached to service accounts, credentials committed to code repositories, and secrets stored in environment variables without encryption. Dedicated secrets management tools (AWS Secrets Manager, Azure Key Vault, HashiCorp Vault) centralise secret storage, enforce rotation, and provide audit trails. The ISM contains specific controls requiring that credentials are not hardcoded and that privileged account credentials are rotated. Credentials exposed in a public repository are indexed by automated scanning tools within minutes.

**Security Service Edge (SSE) and SASE**

SSE is the security-centric convergence of cloud-delivered security services into a unified platform. It combines CASB, Secure Web Gateway (SWG), Zero Trust Network Access (ZTNA), and Firewall-as-a-Service (FWaaS) under a single policy engine. Gartner defined SSE in 2021 as the security-only subset of the broader Secure Access Service Edge (SASE) architecture, which adds networking capabilities such as SD-WAN. PSPF 2025 explicitly references gateway security and SSE capabilities, and includes a new Gateway Security Standard.

```
  SASE ARCHITECTURE

  +-----------------------------------------------------+
  |                      SASE                           |
  |                                                     |
  |   SECURITY SERVICE EDGE (SSE)        |  NETWORKING  |
  |   +----------------------------------+              |
  |   | CASB  |  SWG  |  ZTNA  |  FWaaS |   SD-WAN      |
  |   | Cloud |  Web  |  App   |  Cloud  |              |
  |   | app   |  sec  |  acc   |  FW     |              |
  |   | sec   |       |        |         |              |
  |   +----------------------------------+              |
  +-----------------------------------------------------+
  Delivered as a cloud service; policy enforced at the
  point of access regardless of user location or device
```

**Data Residency and Sovereignty**

Where data physically resides determines which laws apply to it. Cloud regions and availability zones are marketing labels; the legal jurisdiction is what matters. For Australian government entities, OFFICIAL: Sensitive and PROTECTED data must be stored in Australia with a certified HCF provider. PSPF information security requirements mandate that entities implement controls proportional to the sensitivity of their information holdings, which for sensitive data means verified domestic residency, not assumed residency.

## Australian Compliance Landscape

_Full regulatory detail is in [note 03](03.%20Legal,%20Regulatory,%20and%20Compliance.md). Volatile figures are in [note 00](00.%20Current%20Versions%20and%20Facts.md)._


This section covers the specific obligations that apply to Australian government entities, critical infrastructure operators, and their supply chains. These are not advisory — they carry legal and contractual force.

**PSPF 2025**

The Protective Security Policy Framework (PSPF) is the mandatory security policy for non-corporate Commonwealth entities, administered by the Department of Home Affairs. PSPF Release 2025 (July 2025) expanded the security domains from four to six (governance, risk, information, technology, personnel, physical) and significantly uplifted the technology domain.

Cloud-specific PSPF obligations include:

- Entities must manage procurement and outsourcing risk, which explicitly covers cloud service selection.
- Cloud and outsourced systems must be assessed by an IRAP assessor — an Entity Assessor is not sufficient.
- PSPF 2025 embeds Zero Trust principles, with new requirements for gateway security controls (Secure Internet Gateway / SSE platforms) and a new Gateway Security Standard.
- Entities must maintain a Technology Asset Stocktake, which includes cloud-hosted assets.
- AI usage in cloud environments is now explicitly addressed, including requirements for managing emerging technology risks.
- Post-quantum cryptography planning is referenced for long-lived sensitive data.
- Systems of Government Significance (SoGS) face additional mandatory cybersecurity obligations.

PSPF obligations flow through to the private sector via contracts, deeds, panel head agreements, and procurement specifications. A supplier storing or processing Commonwealth data is contractually bound by the relevant PSPF controls.

**ISM (Information Security Manual)**

The ISM, maintained by ASD and updated quarterly, is the technical controls framework that sits beneath the PSPF technology domain. For cloud deployments, the ISM:

- Specifies controls for cryptography, access management, system hardening, logging, and incident management that apply equally to cloud-hosted systems.
- Includes cloud-specific guidance covering data at rest and in transit encryption, multi-tenancy isolation, and CSP security requirements.
- Is the control baseline against which IRAP assessments are conducted.
- Is updated quarterly; assessors must use the version current at the time of assessment commencement.

**IRAP**

The Information Security Registered Assessors Program (IRAP) is ASD's mechanism for independent assessment of cloud systems and CSPs. Key points for practitioners:

- Commonwealth entities must engage an IRAP assessor to assess both the CSP and the entity's own cloud-hosted systems.
- An IRAP assessment produces a Cloud Security Assessment Report against ISM controls and includes the CCM for cloud services.
- The assessment is not a certification or approval to operate. It informs the entity's own risk-based Authority to Operate (ATO) decision.
- IRAP assessors do not make statements of compliance — they document findings, residual risks, and recommended mitigations.
- International certifications (SOC 2, FedRAMP, ISO 27001) do not replace IRAP. No international standard completely aligns to the ISM.
- ASD ceased the Certified Cloud Services List (CCSL) in July 2020. There is no approved CSP list. The IRAP assessment report is the assurance mechanism.

```
  IRAP CLOUD ASSESSMENT PROCESS (SIMPLIFIED)

  Phase 1a: CSP Fundamentals and Cloud Services Assessment
  +---------------------------------------------------------+
  | IRAP assessor reviews CSP security fundamentals        |
  | and in-scope cloud services against ISM controls       |
  | → Cloud Security Assessment Report produced            |
  | → Shared with cloud consumer                           |
  +---------------------------------------------------------+

  Phase 1b (if required): Supplementary Services Assessment
  +---------------------------------------------------------+
  | New or out-of-scope cloud services assessed            |
  +---------------------------------------------------------+

  Phase 2: Cloud Consumer System Assessment
  +---------------------------------------------------------+
  | IRAP assessor reviews entity's own systems built on    |
  | the cloud, identifies inherited and residual controls  |
  | → Cloud Consumer Assessment Report produced            |
  +---------------------------------------------------------+

  Entity Decision: Authority to Operate
  +---------------------------------------------------------+
  | Entity (not IRAP assessor) makes risk-based ATO        |
  | decision based on both assessment reports              |
  +---------------------------------------------------------+
```

**Hosting Certification Framework (HCF)**

The HCF provides certification for data centre and cloud service providers hosting Australian Government data. From 30 June 2022, all new and extended government hosting contracts must use a certified provider. Two certification levels exist:

- **Strategic** — highest assurance; CSP allows the government to specify ownership and control conditions; required for high-risk profiles and PROTECTED-level workloads.
- **Assured** — provides safeguards against change of ownership/control through financial penalties; suitable for lower-risk, sensitive-data workloads.

**Note:** HCF certification registration for new providers was paused in November 2025 pending framework reform. Existing certified providers are not affected. Practitioners should verify current certification status of any CSP via the HCF register before specifying requirements in new contracts.

**SOCI Act 2018 (as amended)**

The Security of Critical Infrastructure Act 2018 applies to entities owning, operating, or with direct interests in critical infrastructure assets across 11 sectors: energy, communications, data storage or processing, financial services and markets, water and sewerage, health care and medical, higher education and research, food and grocery, transport, space technology, and the defence industry.

Cloud-relevant obligations under the SOCI Act:

- **Asset Register** — entities must provide operational and ownership information for critical infrastructure assets to the Register of Critical Infrastructure Assets. Following the 2024 ERP Act amendments (effective December 2024), data storage systems forming part of a primary CI asset are explicitly in scope.
- **Cyber Incident Reporting** — mandatory reporting of cyber incidents impacting critical infrastructure to the ACSC. Significant impact incidents must be reported within 12 hours of the entity becoming aware. For cloud-hosted critical infrastructure, this applies regardless of whether the incident originated with the entity or the CSP.
- **Critical Infrastructure Risk Management Program (CIRMP)** — responsible entities must adopt, maintain, and comply with a written risk management program taking an all-hazards approach across: physical security and natural hazards, personnel hazards, supply chain hazards, and cyber security and information security hazards. CIRMP annual reports were due for the first time in September 2024. Cloud services and their CSPs are material supply chain risks that must be addressed in the CIRMP.
- **Systems of National Significance (SoNS)** — for assets declared SoNS, four Enhanced Cyber Security Obligations (ECSOs) apply, including mandatory incident response exercises, vulnerability assessments, and access for government to gather relevant information.

The SOCI Act's 2024 amendments also explicitly extended data storage systems that hold business critical data (including operational data, encryption keys, network blueprints, and personal information relating to 20,000 or more individuals) as part of the CI asset definition — directly capturing cloud-hosted data stores that previously might have been considered out of scope.

## How It Works in Practice

**Cloud Governance Function**

Mature organisations establish a Cloud Centre of Excellence (CCoE) or equivalent — a cross-functional group spanning security, architecture, operations, finance, and legal. The CCoE owns the cloud strategy, the approved service catalogue, the landing zone design, and the guardrails applied to all provisioned environments. For Commonwealth entities, the CCoE also owns PSPF compliance obligations for cloud, IRAP engagement planning, and HCF procurement requirements.

**Landing Zone Design**

A landing zone is a pre-configured, security-hardened cloud environment that serves as the starting point for all new workloads. It enforces network segmentation, centralised logging, mandatory tagging, permitted regions, and baseline IAM policies before a single workload is deployed.

```
  CLOUD LANDING ZONE — CONTROL LAYERS

  +--------------------------------------------------+
  |  GOVERNANCE LAYER                                |
  |  Policies: permitted regions (AUS only for       |
  |  sensitive data), resource types, mandatory tags,|
  |  cost thresholds, HCF-certified CSP only         |
  +--------------------------------------------------+
  |  IDENTITY LAYER                                  |
  |  SSO integration, MFA enforcement, least-priv    |
  |  IAM roles, no long-term access keys             |
  |  (ISM: privileged account credential rotation)   |
  +--------------------------------------------------+
  |  NETWORK LAYER                                   |
  |  VPC/VNet segmentation, private endpoints,       |
  |  no public IPs by default, NACLs/security groups |
  |  Gateway/SSE for user cloud access (PSPF 2025)  |
  +--------------------------------------------------+
  |  DATA LAYER                                      |
  |  Encryption at rest (KMS/CMK), encryption in     |
  |  transit (TLS 1.2+), data classification tags    |
  |  (OFFICIAL, OFFICIAL: Sensitive, PROTECTED)      |
  +--------------------------------------------------+
  |  LOGGING AND MONITORING LAYER                    |
  |  Centralised log aggregation (immutable),        |
  |  CSPM scanning, SIEM integration, ACSC reporting |
  |  (SOCI: cyber incident reporting capability)     |
  +--------------------------------------------------+
  |  WORKLOADS (deployed into controlled environment)|
  +--------------------------------------------------+
```

**IaC Pipeline Security**

In organisations using IaC for infrastructure provisioning, security controls must be embedded in the pipeline itself. A template is written, scanned for misconfigurations and policy violations, reviewed, and only then permitted to deploy. Secrets scanning catches credentials committed to repositories. Policy-as-code rules enforce the organisation's baseline — permitted regions, mandatory encryption, required tagging — at the code level. For government workloads, policy-as-code rules should directly encode ISM control requirements relevant to cloud deployment (encryption at rest, no public bucket ACLs, required logging configurations).

**CASB Deployment**

A CASB deployment typically begins with discovery: connecting the CASB to existing network egress points or cloud provider logs to baseline what cloud services the organisation is actually using. The discovered service catalogue is reviewed and services are classified as sanctioned, tolerated, or blocked. API connectors are established with key sanctioned applications for deep DLP scanning of data at rest. Inline controls are applied to managed devices for real-time policy enforcement. For government entities, CASB policies should enforce that OFFICIAL: Sensitive and PROTECTED data cannot be transferred to uncertified or unapproved cloud services.

**CSP Assessment and Due Diligence**

For Commonwealth entities: obtain the CSP's IRAP Cloud Security Assessment Report, confirm it is current (ISM version within one update), confirm the HCF certification level matches the data classification requirements, and review the CSP's CCM. Residual controls not inherited from the CSP must be implemented by the entity and assessed in the Phase 2 IRAP assessment.

For non-government entities: review CSA STAR registry, SOC 2 Type II, ISO 27001 certificate, PCI-DSS AOC (where relevant), and penetration test summaries. Contracts must address data residency, incident notification obligations, audit rights, data portability, and obligations on exit. For SOCI entities, the CSP is a supply chain hazard that must be addressed in the CIRMP.

**Cloud Exit and Portability**

Exit planning is frequently neglected. When a CSP relationship ends — voluntarily or due to insolvency, service discontinuation, or regulatory action — organisations need documented processes to extract data, migrate workloads, and verify deletion of all copies. ISO/IEC 27017 includes specific controls on asset removal at contract termination. Under the SOCI Act, loss of access to cloud-hosted CI data or systems due to a CSP failure is a hazard that must be addressed in the CIRMP.

**Ongoing Posture Management**

Day-to-day cloud security management centres on: continuous CSPM scanning to catch configuration drift, regular IAM entitlement reviews, CASB review of sanctioned and unsanctioned service usage, secrets rotation compliance, and cost/resource monitoring to surface abandoned or uncontrolled assets. For PSPF entities, annual IRAP re-assessments or significant change assessments are required to maintain the ATO.

## Common Mistakes and Weaknesses

**Misreading the shared responsibility model.** The most common and most costly mistake. Teams assume the CSP has handled backup, encryption, or access control when those responsibilities sit with the customer. For IRAP-assessed environments, unresolved shared responsibility gaps become findings that prevent the entity from issuing an ATO.

**Assuming IRAP assessment of the CSP is sufficient.** An IRAP report on the CSP covers the CSP's platform. It does not cover the entity's own systems deployed on that platform. Commonwealth entities must separately commission a Phase 2 assessment of their own cloud systems.

**Treating international certifications as IRAP equivalents.** SOC 2 Type II, ISO 27001, and FedRAMP are relevant inputs but do not replace IRAP. The ISM does not fully align with any international standard, and ACSC guidance is explicit that there is no substitute for IRAP assessment when Commonwealth entities are using a CSP.

**Not verifying HCF certification tier against data classification.** A CSP with Assured certification may not be appropriate for PROTECTED-level workloads, which may require Strategic certification. Procurement teams often select a certified provider without checking the tier against the specific classification requirements.

**No approved service catalogue.** Teams provision whatever they need without approval. The result is shadow cloud — resources running outside any security or governance process. For Commonwealth entities, unsanctioned cloud services used to store OFFICIAL: Sensitive data are a direct PSPF breach.

**No CASB or equivalent access control.** Without a CASB or SSE platform, the organisation has no visibility into what cloud services employees are using and no mechanism to enforce access policy for SaaS. PSPF 2025's gateway security requirements make this a compliance gap for Commonwealth entities, not merely a best-practice shortcoming.

**Overpermissive IAM from day one.** Under pressure to ship, teams grant broad permissions (admin roles, wildcard policies, service accounts with full access) and never revisit them. Misconfigured IAM is cited as the primary vector in around one in three cloud breaches.

**Secrets in code.** API keys and credentials committed to IaC templates or application repositories are a persistent failure. Automated tools scan public repositories within minutes of a commit. The ISM's credential management controls apply to cloud service credentials.

**Logging disabled or incomplete.** Cloud environments generate rich telemetry, but it is opt-in. CloudTrail, Azure Monitor, and GCP Cloud Audit Logs require explicit configuration. For SOCI entities, an inability to produce logs for a cyber incident report is a compliance failure on top of a security failure.

**No CIRMP coverage of cloud supply chain.** SOCI entities that operate cloud-hosted CI assets and have not explicitly identified CSPs as supply chain hazards in their CIRMP have a compliance gap. The 2024 ERP Act amendments make data storage systems part of the CI asset definition, directly pulling cloud storage into scope.

**Configuration drift.** An environment that is correctly configured at deployment will drift over time as teams make ad hoc changes outside IaC pipelines. Without continuous CSPM scanning, drift is invisible until it becomes a breach. Average detection time exceeds 180 days.

**No cloud exit plan.** Exit without planning means uncontrolled data retention by the CSP, inability to demonstrate deletion, and operational crisis during any forced migration. For SOCI entities, CSP failure is an all-hazards scenario that must be planned for in the CIRMP.

## Connections to Other Domains

- **[Cyber Governance and Management (1)](01.%20Cyber%20Governance%20and%20Management.md):** Cloud governance is a subset of the broader IT governance function. For Commonwealth entities, PSPF governance obligations — annual security reporting, security planning, and accountability to the Department of Home Affairs and ASD — explicitly include cloud management. The CCoE should report into the entity's security governance structure.

- **[Cyber Risk Management (2)](02.%20Cyber%20Risk%20Management.md):** Cloud introduces specific risks — shared tenancy, loss of physical control, CSP dependency, shadow IT — that require explicit treatment in the risk register. SOCI entities must address cloud risks within their CIRMP under an all-hazards approach. The ISM's risk management framework (drawing from NIST SP 800-37 Rev. 2 and ISO 31000) is the expected methodology for government cloud risk assessment.

- **[Legal, Regulatory, and Compliance (3)](03.%20Legal,%20Regulatory,%20and%20Compliance.md):** Data residency, cross-border transfers, breach notification obligations, PSPF information handling requirements, SOCI Act reporting timelines (12 hours for significant incidents), and HCF procurement requirements are all cloud-specific legal concerns. GDPR, the Australian Privacy Act 1988, APRA CPS 234, and sector-specific rules add further layers.

- **[Privacy and Data Protection (4)](04.%20Privacy%20and%20Data%20Protection.md):** ISO/IEC 27018 directly addresses PII in cloud. The Australian Privacy Act and Australian Privacy Principles (APPs) apply to cloud-processed personal information. Under APP 8, cross-border disclosure of personal information requires the receiving party to provide equivalent protection. Cloud data residency is a privacy law obligation, not only a security preference.

- **[Vendor Management (5)](05.%20Vendor%20Management.md):** CSPs are critical third parties. CSP due diligence, contract terms, SLA management, IRAP assessment review, HCF certification verification, ongoing assurance (STAR, SOC 2), and exit planning are all vendor management activities applied in a cloud context. For SOCI entities, CSPs are supply chain hazards requiring CIRMP treatment.

- **[Asset and Change Management (6)](06.%20Asset%20and%20Change%20Management.md):** Cloud assets are dynamic — instances spin up and down, storage buckets are created and abandoned. PSPF 2025 introduced a Technology Asset Stocktake requirement that includes cloud-hosted assets. IaC and CSPM are the practical tools for managing cloud assets at scale; manual asset tracking is not workable.

- **[Network and Communication Security (7)](07.%20Network%20and%20Communication%20Security.md):** Virtual networks, security groups, private endpoints, peering, and ZTNA all have cloud-native implementations. PSPF 2025 introduced a Gateway Security Standard and explicitly references SSE/SASE as the expected architecture for securing user access to cloud services. The Secure Internet Gateway policy (now under Home Affairs) mandates gateway controls for Commonwealth entities.

- **[Identity and Access Management (8)](08.%20Identity%20and%20Access%20Management.md):** IAM is the most critical control in cloud environments. Cloud-native IAM (AWS IAM, Azure Entra ID, GCP IAM) is complex and easy to over-provision. ISM controls specify requirements for privileged access, MFA, and credential management in cloud. SOCI Act obligations include MFA requirements for CI environments. CASB extends IAM enforcement to unsanctioned cloud services.

- **[Cryptography (9)](09.%20Cryptography.md):** Key management in cloud differs materially from on-premises. Customer-managed keys (CMK), KMS, and key rotation policies must be explicitly designed. The ISM specifies cryptographic requirements applicable to cloud-stored data. PSPF 2025 introduces post-quantum cryptography planning requirements for long-lived sensitive information.

- **[Security Operations and Monitoring (12)](12.%20Security%20Operations%20and%20Monitoring.md):** Cloud telemetry — API call logs, network flow data, configuration change events — must be integrated into security monitoring. SOCI Act mandates cyber incident reporting to the ACSC within 12 hours (significant incidents) or 72 hours (relevant incidents). Many organisations discover post-breach that cloud logging was never integrated with their SOC.

- **[Incident Management and Business Continuity Planning (13)](13.%20Incident%20Management%20and%20Business%20Continuity%20Planning.md):** Cloud changes the recovery landscape. DRaaS, multi-region failover, and automated backup are cloud-native DR capabilities. SOCI entities must address CSP outages as an all-hazards scenario in their CIRMP. SLA uptime commitments do not guarantee availability for every workload.

- **[Software Development Security (15)](15.%20Software%20Development%20Security.md):** IaC is code. The same secure development practices — version control, peer review, static analysis, secrets scanning — apply to infrastructure templates. A misconfigured IaC template is a software vulnerability with infrastructure-wide blast radius.

- **[DevOps and DevSecOps (16)](16.%20DevOps%20and%20DevSecOps.md):** IaC, CI/CD pipelines, policy-as-code, and automated deployment are standard in cloud environments. Security guardrails must be embedded in these pipelines as blocking gates. For government workloads, IaC policy-as-code rules should encode ISM control requirements directly.

- **[Cyber Architecture (17)](17.%20Cyber%20Architecture.md):** Cloud architecture patterns — microservices, serverless, container-based — each have distinct security requirements. Zero-trust architecture is explicitly required under PSPF 2025 (Zero Trust Culture requirement). SSE/SASE is the architectural response to boundary collapse in cloud environments.

- **[LLM Security (19)](19.%20LLM%20Security.md):** Generative AI workloads are predominantly cloud-hosted. LLM deployments introduce additional cloud management concerns: data sent to AI endpoints, model access controls, API key management, and CASB policy controls for shadow AI usage. PSPF 2025 explicitly addresses AI risk, including requirements for managing emerging technology risks and noting the specific risks of AI in cloud environments. PSPF Direction 001-2025 banned DeepSeek products from Commonwealth entities.
