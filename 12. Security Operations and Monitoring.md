# Security Operations and Monitoring

---

## Overview

_Volatile facts (framework versions, requirement numbers, reporting clocks) are maintained in [note 00](00.%20Current%20Versions%20and%20Facts.md). Check it before relying on figures here._

Security operations is the organisational function responsible for continuously monitoring an environment, detecting threats, triaging events, and driving the early stages of response. It sits in the gap between preventive controls — firewalls, IAM policy, endpoint hardening, patch management — and the incident response process. When prevention fails, security operations determines how quickly the organisation knows it has a problem and how quickly it can act. The primary delivery mechanism is the Security Operations Centre (SOC), also called an Information Security Operations Centre (ISOC): a centralised or distributed capability that aggregates telemetry from across the environment, applies detection logic, and produces actionable outcomes. In smaller organisations the SOC may not exist as a dedicated team — monitoring functions may be split across IT operations and security staff, or partially outsourced.

Security operations is distinct from incident response. The SOC detects, triages, and hands off. Incident response takes over from a confirmed or high-confidence incident. The distinction matters for governance, role clarity, resourcing, and measuring effectiveness. In Australia, security operations is subject to a layered set of regulatory obligations that go beyond best practice — mandatory incident reporting windows, prescriptive log retention periods, and enforceable detection capability requirements apply depending on sector and entity type.

---

## Why It Matters

When security monitoring is absent or underfunded, attackers dwell undetected for months. The IBM Cost of a Data Breach Report 2025 found the global average breach lifecycle — time to identify plus time to contain — dropped to 241 days, the lowest in nine years, driven by faster AI-assisted detection. That is still eight months. Breaches exceeding 200 days in duration carry significantly higher costs than those contained quickly. Internal detection shortens breach lifecycles materially compared to breaches disclosed by an attacker.

Real consequences of poor security monitoring:

**Credential-based attacks go undetected for months.** In the IBM 2025 report, breaches initiated with stolen credentials had a mean identification and containment time of approximately 246 days. These attacks blend into normal traffic and are invisible without identity log coverage and behavioural analytics.

**Regulatory reporting windows cannot be met without a functioning SOC.** Under the SOCI Act, significant cyber incidents must be reported to ASD within 12 hours. Under APRA CPS 234, material incidents must be reported within 72 hours. Neither timeline is achievable if the organisation does not detect incidents promptly. Failure to meet these windows carries enforcement consequences.

**Alert fatigue destroys analyst effectiveness.** A SOC that generates thousands of low-quality alerts without triage discipline produces analysts who close alerts without investigation. This is a process and tooling failure, not a headcount problem.

**Coverage gaps are exploited deliberately.** Attackers move toward systems not covered by monitoring — uncovered cloud workloads, SaaS platforms with no audit log export, OT segments, or third-party network zones. If a system does not send logs to the detection platform, it does not exist for monitoring purposes.

**No feedback loop means repeated failure.** When a genuine attack is detected but no new detection rule is written, the next similar attack will again rely on human pattern recognition rather than automated alerting.

**Tool investment without process produces nothing.** A SIEM with default rules, no use case library, and no playbooks is expensive infrastructure without security value. Detection quality is determined by the work put into the platform, not the platform itself.

## Core Concepts

**Event, alert, and incident — why the distinction matters**

An _event_ is any observable occurrence: a login, a file access, a DNS query, a firewall permit or deny. Events are generated continuously at enormous volume. An _alert_ is an event or correlated set of events that meets a detection rule threshold. Not all alerts are incidents. An _incident_ is a confirmed or high-confidence security event requiring a structured response. The SOC's job is to move from event to alert to verified incident efficiently, without missing real threats and without drowning in false positives.

**Detection models**

Detection logic falls into three broad approaches, used in combination:

- _Signature-based_: matches known patterns — malware hashes, known-bad IP addresses, rule-based strings. Fast, low false positive rate, but blind to novel techniques.
- _Behaviour-based (UEBA)_: builds a baseline of normal user and entity activity and flags statistical deviations. Effective against insider threats and living-off-the-land techniques, but requires tuning and produces more noise.
- _Anomaly-based_: uses statistical or ML models to flag outliers in system behaviour. Powerful but data-hungry and prone to false positives without significant tuning and data volume.

Modern detection platforms combine all three. The art is in building use cases that balance coverage with signal quality.

**Detection engineering**

Detection engineering treats detection logic as code: versioned, tested, peer-reviewed, and deployed systematically. Use cases are built against specific adversary techniques (using ATT&CK as the reference), tuned against real environment traffic, reviewed periodically, and updated as infrastructure and threats change. An organisation that treats detection rules as static configuration will fall behind attackers who continuously adapt.

**SOC delivery models**

- _Internal SOC_: Full-time, on-premises staff with dedicated tooling. Highest control and context-retention. Highest cost.
- _Virtual SOC_: Distributed or part-time staff, no dedicated premises.
- _Outsourced / MSSP_: External provider handles some or all monitoring. Reduces internal overhead but introduces dependency and potential visibility gaps.
- _MDR (Managed Detection and Response)_: A more capable outsourced model where the provider brings a defined technology stack, actively investigates alerts, and delivers containment actions. The provider takes outcome accountability rather than simply forwarding alerts.

**Key metrics**

- Mean Time to Detect (MTTD)
- Mean Time to Respond (MTTR)
- Mean Time to Contain (MTTC)
- False positive rate
- Alert volume versus analyst capacity (leading indicator of alert fatigue risk)
- Percentage of alerts closed within SLA
- ATT&CK technique coverage

## Australian Compliance Requirements

_Full regulatory detail is in [note 03](03.%20Legal,%20Regulatory,%20and%20Compliance.md). Volatile figures are in [note 00](00.%20Current%20Versions%20and%20Facts.md)._


### PSPF (Protective Security Policy Framework)

The PSPF applies to non-corporate Commonwealth entities and, in practice, to contractors and suppliers handling Commonwealth data. PSPF Release 2025 (published 24 July 2025) significantly expanded technology security requirements with direct implications for security operations:

**CISO accountability (Requirements 0011 and 0013):** A CISO must be appointed to oversee the entity's cyber security program, including IT and OT. The CISO is accountable to the Accountable Authority for cyber security risks and how the program is managing them. This creates a governance chain that connects SOC performance to executive accountability.

**Cyber Security Strategy (Requirement 0098):** A cyber security strategy and uplift plan must be developed, implemented, and maintained in accordance with the ISM and the Guiding Principles to Embed a Zero Trust Culture. For SOC practitioners, this means monitoring and detection capability must be planned and measurable, not ad hoc.

**Technology Asset Stocktake (Requirement 0211):** A Technology Asset Stocktake and Technology Security Risk Management Plan must be maintained to ensure continuous visibility and monitoring of internet-facing systems and services. This directly requires the kind of coverage mapping that underpins SOC log source management.

**Incident reporting:** Entities must disclose significant security incidents to ASD, incorporate lessons learned in reports, and submit the annual Cyber Security Survey to ASD. The SOC is the mechanism by which significant incidents are detected and confirmed before reporting obligations are triggered.

**ASD Cyber Security Partnership Program (PSPF 2025 new requirement):** Entities are required to engage in ASD's Cyber Security Partnership Program, which includes the Cyber Threat Intelligence Sharing Platform. For SOC teams, this creates a formal channel for operational threat intelligence to feed into detection workflows.

**ISM alignment (Requirement 0085):** ASD ISM controls are applied on a risk-based approach. For monitoring, this means implementing the ISM's prescriptive event logging controls detailed below.

### ASD ISM — System Monitoring Controls

The ISM (updated quarterly; verify the current release at cyber.gov.au) contains specific controls for event logging and monitoring that are the technical implementation standard for PSPF-compliant environments:

```
  ISM Control Summary — Event Logging and Monitoring

  ISM-0580: An event logging policy is developed, implemented and maintained.
  ISM-1405: A centralised event logging facility is implemented.
  ISM-1983: Event logs are sent to the centralised facility as soon as possible
            after they occur.
  ISM-1984: Event logs sent to the facility are encrypted in transit.
  ISM-1985: Event logs are protected from unauthorised access.
  ISM-1815: Event logs are protected from unauthorised modification and deletion.
  ISM-0988: An accurate and consistent time source is used for event logging.
  ISM-0585: For each event: date and time, user/process, filename, event
            description, and IT equipment involved are captured.
  ISM-1959: Event logs are captured and stored in a consistent, structured format.

  Analysis requirements:
  ISM-1986: Event logs from critical servers are analysed in a timely manner.
  ISM-1906: Event logs from internet-facing servers are analysed in a timely manner.
            (Essential Eight ML2, ML3)
  ISM-1907: Event logs from non-internet-facing servers are analysed in a timely
            manner. (Essential Eight ML3)
  ISM-0109: Event logs from workstations are analysed in a timely manner.
            (Essential Eight ML3)
  ISM-1987: Event logs from security products are analysed in a timely manner.
  ISM-1960: Event logs from internet-facing network devices are analysed in a
            timely manner.
  ISM-1228: Cybersecurity events are analysed in a timely manner to identify
            cybersecurity incidents. (Essential Eight ML2, ML3)

  Retention:
  ISM-1988: Event logs are retained in a searchable manner for at least 12 months.
  ISM-1989: Event logs are retained per National Archives of Australia AFDA
            Express Version 2 minimum retention requirements.
```

The ISM is updated quarterly by ASD. Controls should be verified against the current version at cyber.gov.au rather than relying on any static reference.

**Practical implication:** ISM-1988 sets a 12-month searchable retention floor. ISM-1989 requires compliance with AFDA Express retention schedules. Many categories of government records under AFDA Express require retention of 7 years or longer. A SOC operating under the ISM cannot rely on 90-day hot storage as a complete answer — the retention architecture must satisfy both the searchability requirement and the AFDA schedule relevant to the record class.

### SOCI Act — Critical Infrastructure Operators

The SOCI Act 2018, as significantly amended by the SLACI Act 2021 and SLACIP Act 2022, covers 11 critical infrastructure sectors. All responsible entities must:

**Critical Infrastructure Risk Management Program (CIRMP):** Maintain a written risk management program covering cyber and information security hazards (as well as physical, personnel, and supply chain hazards). The CIRMP must be reported on annually within 90 days of 30 June. The program must align to one of the five designated frameworks — Essential Eight, NIST CSF, ISO 27001/27002, AESCSF, and C2M2 — or an equivalent framework. Detection and monitoring capability must be addressed within the cyber hazards component of the CIRMP.

**Mandatory cyber incident reporting:** If a cyber security incident has a significant impact on the availability of a critical infrastructure asset, the responsible entity must report to ASD within **12 hours** of becoming aware. If the impact is relevant (but not significant), reporting must occur within **72 hours**. These windows make a functioning, 24/7 detection capability a practical necessity, not just a compliance requirement. The SOC is the mechanism by which the organisation becomes aware in time to meet these obligations.

**Enhanced Cyber Security Obligations (ECSOs) for Systems of National Significance (SoNS):** Entities whose assets are declared SoNS face additional obligations including mandatory cyber security incident response planning and mandatory cyber security exercises. Monitoring capability must be demonstrated, not merely attested.

**2024 amendments:** Data storage systems holding business-critical data of entities in scope are now also captured. This extends CIRMP and monitoring obligations to data infrastructure supporting critical assets.

**Practical implication for SOC teams:** The 12-hour reporting window for significant impacts means the SOC must have clear escalation criteria, defined severity thresholds, and rapid notification pathways to the CISO and Accountable Authority. Alert-to-escalation workflows must be designed with these windows as a hard constraint.

### APRA CPS 234 — Financial Sector

APRA CPS 234 (in force 1 July 2019) applies to all APRA-regulated entities: authorised deposit-taking institutions (banks, credit unions), general and life insurers, private health insurers, and superannuation RSE licensees. Where information assets are managed by a third party, the requirements extend to that third party.

CPS 234's detection requirements are explicit: entities must have **robust mechanisms in place to detect and respond to information security incidents in a timely manner**. CPG 234 (APRA's accompanying guidance) makes clear that detection mechanisms include scanning, sensing, and logging — and that monitoring must include identification of unusual patterns of behaviour. This is, in effect, a regulatory mandate for the core capabilities of a SOC.

Key monitoring-related obligations under CPS 234:

- Maintain an information security capability commensurate with threats to information assets
- Have information security response plans covering all stages from **detection** to post-incident review
- Escalate and report incidents to the Board, governing bodies, and individuals responsible for incident management
- Test the effectiveness of information security controls through a systematic testing program
- Notify APRA as soon as possible and no later than **72 hours** after becoming aware of a material incident
- Report material information security control weaknesses to APRA as soon as possible and no later than **10 business days** after identification

The 72-hour APRA notification window parallels the SOCI Act 72-hour obligation and reinforces that detection timeliness is a regulatory output measure, not an internal operational aspiration.

## How It Works in Practice

**Telemetry collection and coverage**

A SOC is only as good as its visibility. Effective coverage requires telemetry from across the environment:

- _Endpoint_: EDR agents capturing process execution, file activity, network connections, registry changes
- _Network_: Firewall logs, proxy/web gateway logs, DNS query logs, NetFlow/IPFIX, NDR for behavioural analysis, IDS/IPS
- _Identity_: Authentication events, privileged access, IAM changes, MFA events, service account activity
- _Cloud_: CloudTrail, Azure Monitor, GCP Audit Logs, VPC flow logs, container and Kubernetes logs, CSPM alerts
- _Applications_: Web application logs, API gateway logs, SaaS audit logs (often requiring premium licences to enable export)
- _OT/ICS_: For SOCI-regulated entities with operational technology, OT network visibility is a CIRMP requirement

The ISM's Technology Asset Stocktake requirement (PSPF Requirement 0211) provides a regulatory forcing function for comprehensive coverage mapping. ATT&CK data source mappings provide a systematic method for identifying which log sources are needed to detect each technique and where gaps exist.

**SIEM as the correlation engine**

The SIEM aggregates, normalises, and correlates events. It applies detection rules, enriches alerts with threat intelligence, and surfaces alerts. The ISM explicitly names SIEM and SOAR as appropriate platforms for the centralised event logging facility (ISM-1405). Log normalisation is a prerequisite — different sources produce logs in different formats (JSON, CEF, syslog, proprietary). Schemas including OCSF and ECS enable consistent field mapping for correlation.

**SOAR for automation and consistency**

SOAR connects SIEM, threat intelligence platforms, ticketing systems, and response tools, executing predefined playbooks. Common automation workflows include: alert enrichment with threat intelligence, identity system lookups, endpoint isolation on confirmed malware, and incident ticket creation with pre-populated context. The IBM 2025 report found extensive AI and automation in security operations cut the breach lifecycle by an average of 68 days and saved approximately USD 1.9 million per breach.

**Threat intelligence integration**

Operational threat intelligence (IOCs) is ingested into the SIEM for automated matching. ASD's Cyber Threat Intelligence Sharing Platform — now a mandatory ASD Cyber Security Partnership Program engagement under PSPF 2025 — provides a government-level feed of actionable threat intelligence for Commonwealth entities.

**Threat hunting**

Threat hunting is proactive and hypothesis-driven: analysts search for adversary behaviour that has not triggered an alert. Hunts are grounded in ATT&CK techniques, recent threat intelligence, or environmental anomalies. A hunt that finds activity produces both an incident and a new detection rule.

**Cloud monitoring considerations**

Cloud environments require adapted approaches. Cloud-native log sources differ from on-premises equivalents. Key considerations: connector-based log ingestion for each cloud service; streaming capture for ephemeral workloads; CSPM for configuration drift; SaaS audit log export configuration. For PSPF-covered entities, cloud services must be IRAP-assessed or use assessed hosting under the Hosting Certification Framework.

**Data retention**

ISM-1988 requires event logs to be retained in a searchable manner for at least 12 months. ISM-1989 requires compliance with AFDA Express Version 2 retention schedules for Commonwealth records, which can require significantly longer retention for certain record classes. A practical layered approach for Australian government and regulated environments:

- Hot / searchable (SIEM): 12 months minimum (ISM-1988)
- Warm / retrievable: As required by AFDA Express schedules and CIRMP obligations
- Cold / archived: Per applicable regulatory and records obligations — potentially 7+ years for certain record classes

For APRA-regulated entities: retention must support the ability to investigate incidents over a timeframe consistent with realistic dwell times. The 241-day average breach lifecycle from IBM 2025 is a useful planning input.

## Common Mistakes and Weaknesses

**No use case management discipline**
Deploying a SIEM with vendor default rules produces noise calibrated to generic environments. Without a structured use case library, ATT&CK coverage mapping, and regular review cycles, the platform has limited detection value. This also creates a compliance risk: ISM-1228 requires timely analysis to identify cybersecurity incidents — "alerts exist but no one looks at them" is not compliant.

**Alert fatigue eroding analyst performance**
When analysts process hundreds of low-quality alerts per shift, they begin closing alerts faster without thorough investigation. The answer is rule tuning, suppression of known-good activity, and SOAR automation — not adding headcount to process noise.

**Coverage gaps in log sources**
Common gaps: cloud workload logs, SaaS audit logs (often gated behind premium licences), OT/SCADA environments, third-party network segments. For PSPF entities, the Technology Asset Stocktake is a forcing function for coverage mapping. For SOCI entities, CIRMP cyber hazard documentation should reflect monitoring coverage.

**Missing the ISM retention and log integrity requirements**
ISM-1988 (12-month searchable), ISM-1984 (encrypted in transit), ISM-1985 (protected from unauthorised access), and ISM-1815 (protected from modification and deletion) are individually verifiable controls. Organisations frequently implement logging but fail on log integrity protection. This creates both a security and a compliance gap — if logs can be modified, they cannot be relied upon for incident investigation or as evidence.

**No detection feedback loop**
When a confirmed true positive is investigated but no new detection rule is produced, the next similar attack will rely on human pattern recognition. The SOC must have a formal process for converting investigation findings into improved detection.

**MTTD and MTTR not measured**
Under SOCI's 12-hour window and APRA's 72-hour window, MTTD is a compliance input. An organisation that cannot state its current MTTD cannot demonstrate that it is capable of meeting its reporting obligations. These metrics require agreed definitions, consistent tooling, and leadership visibility.

**Treating the SOC as a compliance checkbox**
Building monitoring capability to satisfy an audit requirement rather than to detect real attacks produces a capability that looks correct on paper but fails operationally. The PSPF's shift from maturity reporting to evidence-based reporting (92% of NCEs reporting effective compliance in 2024-25, unverified — confirm against the PSPF Assessment Report) means the ASD and Department of Home Affairs are increasingly looking for demonstrable outcomes, not just documented intentions.

**Outsourcing without retained oversight**
MSSP and MDR relationships where the internal team has no visibility into detection logic, use case coverage, alert quality, or investigation outcomes create dependency without governance. For APRA-regulated entities, CPS 234's requirement for robust detection mechanisms cannot be delegated away — the entity remains accountable and must be able to demonstrate the provider is meeting the standard. Contractual SLAs should specify coverage scope, detection use cases, and escalation timeframes.

**Insufficient clock synchronisation**
Log timestamps from sources not synchronised via NTP make timeline reconstruction unreliable during forensic investigation. ISM-0988 is explicit. This is a common finding in post-incident reviews and cheap to fix proactively.

## Connections to Other Domains

- **[Threat Intelligence (11)](11.%20Threat%20Intelligence.md):** Directly feeds the SOC. Tactical intelligence (IOCs) enriches SIEM alerts in near real time. ASD's Cyber Threat Intelligence Sharing Platform (a PSPF 2025 mandatory engagement for Commonwealth entities) provides a government-level feed. Strategic intelligence shapes detection engineering priorities and threat hunt hypotheses.

- **[Incident Management and Business Continuity Planning (13)](13.%20Incident%20Management%20and%20Business%20Continuity%20Planning.md):** The SOC is the detection engine; incident management is the response engine. The handoff — escalation criteria, communication protocols, ownership transfer — must be clearly governed. Under SOCI and APRA CPS 234, the handoff must also feed directly into the mandatory reporting process. Failure at this boundary delays regulatory notifications and compounds consequences.

- **[Cyber Risk Management (2)](02.%20Cyber%20Risk%20Management.md):** SOC investment decisions, coverage priorities, SLA targets, and use case priorities should be driven by the organisation's risk profile. For SOCI entities, the CIRMP requires a formal risk-based approach to cyber hazards that must connect to monitoring capability decisions.

- **[Asset and Change Management (6)](06.%20Asset%20and%20Change%20Management.md):** You cannot monitor what you do not know exists. The asset register and CMDB are direct inputs to log source coverage planning. The ISM's Technology Asset Stocktake (PSPF Requirement 0211) makes this a mandatory exercise for Commonwealth entities. Change management events should also feed the SIEM — a new service is expected post-change, suspicious otherwise.

- **[Identity and Access Management (8)](08.%20Identity%20and%20Access%20Management.md):** Authentication logs, privileged access events, MFA anomalies, and IAM changes are among the highest-value detection sources. Identity-based attack patterns — credential stuffing, Pass-the-Hash, lateral movement via legitimate accounts — are only visible with full identity log coverage and UEBA capability. ISM controls require logging of access to systems and data.

- **[Network and Communication Security (7)](07.%20Network%20and%20Communication%20Security.md):** Firewall logs, DNS, NetFlow, proxy logs, and IDS/IPS alerts are foundational SOC input. NDR tools feed into SOC detection workflows. For SOCI entities with OT environments, OT network visibility is a CIRMP cyber hazards obligation.

- **[Cyber Testing (10)](10.%20Cyber%20Testing.md):** Purple team exercises and red team engagements directly test SOC detection capability. Findings should immediately feed the detection engineering backlog. APRA CPG 234 explicitly expects testing of detection control effectiveness. ECSOs under SOCI mandate cyber security exercises for SoNS entities.

- **[Cloud Management (14)](14.%20Cloud%20Management.md):** Cloud environments generate distinct telemetry requiring adapted detection logic. CSPM feeds configuration drift alerts. For PSPF entities, cloud services must be IRAP-assessed; the SOC must maintain visibility into IRAP-assessed cloud environments through appropriate log ingestion.

- **[Cyber Governance and Management (1)](01.%20Cyber%20Governance%20and%20Management.md):** SOC mandate, authority, resourcing, and escalation paths must come from governance. Under PSPF 2025, the CISO is accountable to the Accountable Authority for cyber security risks and how the program manages them — the SOC's performance is a direct input to this accountability chain.

- **[Cyber Architecture (17)](17.%20Cyber%20Architecture.md):** SOC telemetry requirements must be embedded in architectural decisions. Security architects must ensure new systems produce, export, and route logs before reaching production. For IRAP-assessed systems, System Security Plans must document the event logging and monitoring approach against ISM controls.

- **[LLM Security (19)](19.%20LLM%20Security.md):** Emerging detection use cases include prompt injection attempts, abnormal LLM API usage patterns, and shadow AI. PSPF 2025 introduces new AI-specific policy content (Section 13.10.1) that references existing monitoring and access control requirements as applying to AI systems. IBM 2025 found shadow AI contributed approximately USD 670,000 to average breach costs in affected organisations.
