# DevOps and DevSecOps

---

## Overview

_Volatile facts (framework versions, requirement numbers, reporting clocks) are maintained in [note 00](00.%20Current%20Versions%20and%20Facts.md). Check it before relying on figures here._

DevOps is a set of cultural practices, workflows, and toolchains that break down the traditional wall between software development and IT operations. The goal is to deliver software faster, more reliably, and with tighter feedback loops between teams and between code and production. DevSecOps extends this by integrating security into every stage of that lifecycle — not as a gate at the end, but as a continuous, automated, shared responsibility. In the broader security landscape, DevSecOps sits at the intersection of software development security, cloud management, and security operations. It is where security policy becomes executable: policies enforced in pipelines, controls baked into infrastructure templates, and risk decisions embedded in deployment gates rather than in quarterly review meetings.

The shift matters because modern software delivery is too fast and too automated for manual security reviews to keep pace. An organisation pushing hundreds of deployments per day cannot rely on a security team signing off each release. It must encode its security requirements into the pipeline itself.

---

## Why It Matters

When DevSecOps is done poorly, security becomes an afterthought applied to software that is already live and difficult to change. The consequences are well-documented:

**SolarWinds (2020):** Attackers compromised the build pipeline for SolarWinds' Orion platform, injecting malicious code (Sunburst) into legitimate, signed software updates distributed to over 18,000 organisations including US government agencies. The build system itself was the attack surface — not the application code. No pipeline integrity controls detected the injection.

**Log4Shell (2021):** A critical vulnerability in the Log4j library cascaded through thousands of applications. Organisations without software composition analysis (SCA) in their pipelines had no automated way to identify which of their products were affected and no SBOM to consult. Response time correlated directly with whether organisations had component inventory.

**3CX Supply Chain Attack (2023):** A compromised open-source library was used to infect the 3CX softphone application, which then delivered malware to end users. The attack vector was an unverified, tampered dependency in the build pipeline — a problem that provenance controls and SBOM generation would have surfaced.

**XZ Utils (2024):** A malicious actor spent nearly two years contributing to the XZ Utils open-source project before inserting a backdoor into a release shipped in several Linux distributions. This was a social engineering attack on the open-source supply chain — a category that automated scanning cannot fully address, but SBOM tracking and provenance verification reduce exposure.

Common consequences of poor DevSecOps practice: vulnerabilities shipped to production and found by attackers first; credentials committed to repositories and exploited before being rotated; insecure IaC templates deployed at scale; no audit trail of who built what from which source; and no way to answer "are we affected?" during a zero-day response.

## Core Concepts

### The DevOps Infinity Loop

DevOps operates as a continuous loop moving through planning, coding, building, testing, releasing, deploying, operating, and monitoring — then back to planning. DevSecOps inserts security checks, automated controls, and feedback at each stage rather than placing a single security review at the release gate.

```
         PLAN ──────── CODE  ────────
        /        (threat model,          \
  MONITOR         secure stories)       BUILD
      |                                   |
   OPERATE                             TEST
 (runtime       (SAST, SCA, secret scan,
  security)      IaC scan, SBOM gen)
        \                               /
        DEPLOY ──────────────── RELEASE
        (immutable, signed,    (DAST, policy gate,
         policy enforcement)    provenance attestation)
```

### Shift Left — and Shift Everywhere

"Shifting left" means moving security activities earlier in the SDLC, closer to where code is written. Finding a vulnerability in a developer's IDE is cheap. Finding it in production after exploitation is not. Shift left is implemented through pre-commit hooks, pull-request security checks, and CI pipeline controls that run before code reaches staging or production.

"Shift left" does not mean security only happens early. It means security is continuous, with the right check at the right stage. Static analysis happens at commit; dynamic testing happens at pre-deployment; runtime monitoring happens in production. A better mental model is "security everywhere."

### CI/CD Pipelines

Continuous Integration (CI) merges code frequently and automatically builds and tests the result. Continuous Delivery/Deployment (CD) automates packaging and deployment of validated builds. In a DevSecOps context, the pipeline is where security controls are enforced: SAST, SCA, container image scanning, secret detection, IaC linting, and policy gates all run automatically with every pipeline execution. The pipeline is not just a delivery mechanism — it is a security control.

### Infrastructure as Code (IaC)

Infrastructure is defined in code (Terraform, Bicep, CloudFormation, Pulumi, Ansible) rather than provisioned manually. This enables version control, peer review, and automated scanning of infrastructure changes. It also means a misconfiguration in a template can propagate at scale. IaC scanning tools (Checkov, tfsec, KICS) check templates before they are applied. Infrastructure configuration must receive the same security review as application code.

### GitOps

GitOps extends IaC by using Git as the single source of truth for declarative infrastructure and application state. Changes are proposed via pull requests, reviewed, approved, and then automatically reconciled into the target environment by a GitOps operator (ArgoCD, FluxCD). Security benefits: a full audit trail of all infrastructure changes in Git history; branch protection and required approvals enforced; detection and alerting on configuration drift between the repository and the running environment; and rapid rollback by reverting a Git commit.

GitOps makes every infrastructure change go through the same review and approval process as application code, which is a material improvement over ad-hoc console changes that leave no traceable record.

### Immutable Infrastructure

Rather than patching running servers, immutable infrastructure replaces them. A new container image or VM image is built, scanned, and deployed; the previous one is destroyed. This eliminates configuration drift, ensures the running environment matches what was tested, and reduces the attack surface of long-lived systems.

### Security as Code (SaC)

Security as Code means every security control — access control policies, firewall rules, compliance requirements, vulnerability scan thresholds — is expressed in code, version-controlled, and deployed through the same pipeline as the application. This provides: consistency (the same policy applies everywhere the code deploys); auditability (changes are tracked in Git); and automation (controls apply without manual intervention). SaC converts security policy documents into enforced, testable controls.

### Policy as Code

Policy as Code is a specific application of SaC where organisational policies are expressed in a declarative language and evaluated automatically at pipeline or runtime. Open Policy Agent (OPA) with its Rego language is the dominant open-source solution. In Kubernetes environments, OPA Gatekeeper or Kyverno enforces admission policies — blocking non-compliant workloads from deploying. In IaC pipelines, HashiCorp Sentinel enforces policies on Terraform plans before apply. Typical policies: "only signed images from the approved registry may be deployed"; "no container may run as root"; "all S3 buckets must have encryption enabled."

### Threat Modelling in DevSecOps

Threat modelling identifies what can go wrong before it is built. In DevSecOps it is performed at design time — during sprint planning when new features or architectural changes are being scoped — not as a pre-release exercise. The STRIDE framework (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) applied to data flow diagrams is the most widely used approach.

In practice: when a new service is being designed, the team draws a data flow diagram, identifies trust boundaries, enumerates threats using STRIDE, and records mitigations as security requirements that become backlog items. This converts threat modelling from a documentation exercise into actionable development work.

For CI/CD pipelines and GitOps workflows, STRIDE can be applied to the pipeline data flows themselves — identifying where a compromised build step, a tampered image, or a stolen signing key could enable a supply chain attack.

### Software Bill of Materials (SBOM)

An SBOM is a structured, machine-readable inventory of all components in a software product — libraries, frameworks, dependencies, their versions, and provenance. SBOMs enable rapid impact assessment when a vulnerability is disclosed (as organisations with SBOMs proved during Log4Shell), support licence compliance, and are increasingly required by regulation.

The two dominant SBOM formats are **SPDX** (ISO/IEC 5962:2021) and **CycloneDX** (OWASP). Both are machine-readable (JSON, XML) and supported by major SBOM generation tools (Syft, cdxgen, Trivy). The EU CRA mandates SBOMs in machine-readable format covering at least top-level dependencies. SBOM generation must be part of every build, with the resulting file stored alongside the artefact and updated on every release.

### Software Supply Chain Security

The software supply chain encompasses everything that contributes to a software artifact: source code, build tools, dependencies, CI/CD infrastructure, package registries, and signing infrastructure. Supply chain attacks target these intermediary components. Supply chain security requires provenance — verifiable, cryptographically attested evidence of where an artifact came from and how it was built. SLSA provides the framework for achieving and communicating this assurance level.

### DORA Metrics

The DevOps Research and Assessment (DORA) group has identified four key metrics that measure software delivery performance. These are the industry standard for assessing whether a DevOps programme is working, and they are relevant to security practitioners because high-performing teams demonstrate better security outcomes alongside faster delivery.

```
Metric                     What it measures
──────────────────────     ─────────────────────────────────────────────
Deployment Frequency       How often changes are deployed to production
Lead Time for Changes      Time from commit to successful production deploy
Change Failure Rate        Percentage of deployments causing production failures
Time to Restore            Time to recover from a production failure or outage
```

The 2024 DORA report (based on 39,000+ respondents globally) found that only 19% of teams reached elite performance. Elite teams deploy on demand, with lead times under one day, change failure rates around 5%, and recovery times under an hour. Security practitioners should use these metrics to demonstrate that DevSecOps investment improves delivery outcomes alongside security posture — they are not in tension.

## How It Works in Practice

### Pipeline Security Controls

A mature DevSecOps pipeline integrates security controls at each stage. The sequence below draws from NIST SP 800-204D, OWASP guidance, and common enterprise implementations:

```
Developer Workstation
  |
  +-- [Pre-commit hooks]
  |     Secret scanning (gitleaks, detect-secrets)
  |     Linting, formatting, basic static checks
  |
  v
Source Repository (Git)
  Branch protection rules, required reviewers, signed commits
  |
  +-- [Pull Request / CI Build]
  |     SAST: Static Application Security Testing
  |       (Semgrep, Checkmarx, SonarQube, CodeQL)
  |     SCA: Software Composition Analysis
  |       (Dependabot, Snyk, OWASP Dependency-Check, Renovate)
  |     IaC Scanning (Checkov, tfsec, Trivy, KICS)
  |     Full-history secret scan (Gitleaks, truffleHog)
  |     Threat model review gate for architectural changes
  |
  v
Build Pipeline (containerised, reproducible build environment)
  |     SBOM generation (Syft, cdxgen, CycloneDX)
  |     Container image scan (Trivy, Grype, Wiz)
  |     Image signing (Cosign / Sigstore)
  |     SLSA provenance attestation
  |     Artefact published to registry with signature + SBOM
  |
  v
Pre-Deployment Gate
  |     Policy as Code enforcement (OPA / Gatekeeper / Kyverno)
  |       Checks: image signed? SLSA level met? Critical CVEs resolved?
  |     DAST: Dynamic Application Security Testing
  |       (OWASP ZAP, Burp Suite Enterprise)
  |     Compliance scan against CIS Benchmarks or internal baseline
  |
  v
Production Deployment (GitOps via ArgoCD / FluxCD)
  |     Immutable infrastructure / blue-green / canary deployment
  |     Runtime security monitoring (Falco, eBPF-based tooling)
  |     Continuous compliance and drift detection
  |     Anomaly alerts feed back to development teams
```

### Cloud-Native Architecture Example

The AWS pipeline architecture below illustrates a cloud-native DevSecOps implementation. Separate pipelines for staging and production flow through CodePipeline, with build steps in CodeBuild, artefacts in S3 and container images in ECR, and workloads on ECS behind ALBs and AWS WAF. Security services — KMS, IAM, CloudWatch — are integrated as platform-level controls.

```
CodeCommit / GitHub
       |
  CodePipeline
  /            \
CodeBuild      CodeBuild
(Staging)      (Prod)
  |               |
CodeDeploy     CodeDeploy
(Staging)      (Prod)
  |               |
 ECS (ALB + WAF) ECS (ALB + WAF)

Artefacts: S3 (build), ECR (images)
Controls:  KMS (encryption), IAM (least-privilege pipeline roles),
           CloudWatch (logging and monitoring)
```

IAM roles for the staging pipeline should not have permission to deploy to production. Images in ECR should be scanned on push and policy enforcement should block unscanned or unsigned images from being pulled by production tasks.

### Docker Architecture: Registry as a Trust Boundary

The Docker model below illustrates a critical trust boundary: the container registry. If an image in the registry is tampered with or contains a vulnerability, every container instance spun from it inherits that problem.

```
Client              Docker Host              Registry
──────              ───────────              ────────
docker build ──>                             Signed, scanned
docker pull  ──>    Docker daemon  <──────   images only
docker run   ──>    (creates container)      (ECR, GCR, GHCR,
                    from image               JFrog Artifactory)

Required controls:
  - Image signed with Cosign before push
  - Image scanned (Trivy, Grype) before push and on pull
  - Admission policy denies unsigned / unscanned images
  - Registry access controlled by IAM (least-privilege pull tokens)
  - Audit logging on all pull/push operations
```

### Roles in Practice

**Developers** run SAST and SCA in their IDEs or via pull-request checks and are responsible for fixing findings in their own code. They receive actionable alerts with remediation guidance — not raw vulnerability dumps ranked by CVSS alone.

**Platform and DevOps engineers** own the pipeline. They ensure security tooling is integrated, cannot be bypassed, and is maintained. They enforce branch protection, signed commits, immutable build environments, and least-privilege pipeline service accounts.

**Security engineers** define policies, tune tooling, triage high-severity findings requiring architectural decisions, and run the manual testing (penetration testing, red team exercises, threat modelling workshops) that automated tooling cannot replace.

**Security champions** are developers with additional security training embedded in development teams. They act as the first line of security review, bridge the cultural gap, and reduce bottleneck load on the central security team.

### DSOMM Maturity Levels

The OWASP DevSecOps Maturity Model provides a useful reference for assessing where an organisation sits and what to prioritise next:

```
Level 0: Ad-hoc, reactive. Security isolated in a dedicated team.
         Manual processes. Reviews happen late in the release cycle.

Level 1: Foundations forming. Basic awareness. Initial vulnerability
         scanning. Simple policy documentation. Security tools
         introduced but not consistently enforced.

Level 2: Formalising. Security embedded in some teams.
         Automated scanning in CI pipelines. Security champions
         in place. Findings tracked and actioned.

Level 3: Systematic. Standardised processes across teams.
         Automated gates in pipelines. SBOM generated per build.
         Threat modelling at design time. Monitoring and metrics.

Level 4: Optimising. Security embedded in organisational culture.
         Policy as Code. Blue/green deployments. Continuous
         compliance. AI/ML-assisted detection. Proactive supply
         chain controls at SLSA L2+.
```

### Measuring DevSecOps Effectiveness

Beyond the DORA four-key metrics, track:

- Mean time to remediate (MTTR) by severity — trend over quarters
- Percentage of builds passing all security gates without exceptions
- Secrets-in-code incidents per quarter — trend to zero
- SBOM coverage as a percentage of production services
- Percentage of deployed images with valid SLSA provenance
- Number of security exceptions (pipeline bypasses) granted per quarter — each one is a risk decision that should be reviewed

## Common Mistakes and Weaknesses

**Treating DevSecOps as tooling rather than culture.** Organisations install SAST tools and declare victory. If findings are not actioned or fedback to developers in a usable way, the tools produce noise rather than improvement. Developers learn to ignore alerts that are too numerous, too vague, or not their responsibility to fix.

**Alert fatigue from uncalibrated tools.** A SAST tool with a high false positive rate trains developers to dismiss its output. Tuning for high-signal, low-noise output — prioritising exploitability over raw CVSS score — is critical to keeping developers engaged. Severity triage matters more than finding everything.

**Secrets in source code.** Despite years of awareness, hardcoded credentials remain a consistently common finding. Exposures persist because a secret was committed to a private repository later made public, or because the historical commit was not cleaned from Git history after removal. Secret scanning must run on full commit history, not just current HEAD.

**Overprivileged CI/CD service accounts.** Build pipelines often run with excessive permissions — a compromised pipeline can access production systems, exfiltrate secrets, or deploy malicious artefacts. Least privilege applies to pipeline service accounts exactly as it does to human users. Separate credentials for build, test, staging deploy, and production deploy are a minimum.

**No separation between build and deploy credentials.** Using the same credentials to build and deploy means a compromised build environment can deploy anything to production without additional authorisation. These should be separate, scoped to the minimum required action, and time-limited (ephemeral tokens).

**Unverified third-party dependencies.** Pulling packages from public registries without SCA, version pinning, or allow-lists exposes the application to dependency confusion, typosquatting, and known-vulnerable components. Private registry mirrors with allow-lists reduce this surface significantly.

**IaC deployed without scanning.** Misconfigured S3 buckets, open security groups, disabled encryption, and overly permissive IAM roles frequently originate in unreviewed Terraform or CloudFormation. IaC scanning must be mandatory in the pipeline, with gates that block misconfigurations before apply.

**No SBOM, no visibility.** Without a component inventory, an organisation cannot answer "are we affected?" in a timely way. Log4Shell made this concrete: organisations with SBOMs answered within hours; those without took days to weeks. SBOM generation must be part of every build.

**Shadow pipelines.** Development teams create unofficial pipelines that bypass approved tooling — typically for speed or out of frustration with the approved process. The fix is to make the secure path the easy path: fast pipelines with minimal friction for compliant code.

**DevSecOps without threat modelling.** Automated scanning finds known vulnerability patterns. Threat modelling finds architectural flaws and logic errors that scanners cannot detect. Organisations that rely solely on pipeline tooling miss entire categories of risk. Threat modelling at design time is not optional.

**AI-assisted coding without adjusted controls.** The 2024 DORA report found that AI tool adoption correlated with larger change batch sizes, which increased change failure rates. AI-generated code must go through the same SAST, SCA, and peer review as human-written code — and the pipeline must not be relaxed for AI-generated output.

## Connections to Other Domains

- **[Software Development Security (15)](15.%20Software%20Development%20Security.md):** DevSecOps is the operational implementation of secure development principles. SDLC controls, threat modelling methods, secure coding standards, and vulnerability disclosure processes from that domain are enforced and automated through the pipeline.

- **[Cloud Management (14)](14.%20Cloud%20Management.md):** Cloud-native DevSecOps depends on cloud platform capabilities — managed build services, container registries, IAM, secrets management, policy enforcement, and runtime monitoring. Cloud security posture management (CSPM) and DevSecOps controls are tightly coupled.

- **[Asset and Change Management (6)](06.%20Asset%20and%20Change%20Management.md):** Every pipeline run is a change event. SBOM generation, artefact versioning, deployment records, and Git commit history are the mechanisms by which software assets are tracked and changes are controlled with an auditable record.

- **[Identity and Access Management (8)](08.%20Identity%20and%20Access%20Management.md):** Pipeline service accounts, repository access controls, signing key management, secrets management, and RBAC on registry operations are all IAM problems expressed in a DevSecOps context. Overprivileged pipelines and shared credentials are persistent weaknesses.

- **[Cyber Testing (10)](10.%20Cyber%20Testing.md):** SAST, DAST, SCA, fuzz testing, and penetration testing are forms of security testing integrated at different points in the lifecycle. Periodic red team exercises and penetration tests provide assurance that automated pipeline testing is not missing entire vulnerability classes.

- **[Threat Intelligence (11)](11.%20Threat%20Intelligence.md):** Vulnerability feeds from NVD, OSV, and vendor advisories power SCA tools. Current threat intelligence on actively exploited CVEs informs prioritisation — exploitability in the wild matters more than raw CVSS score when triaging remediation.

- **[Security Operations and Monitoring (12)](12.%20Security%20Operations%20and%20Monitoring.md):** Runtime security monitoring — detecting anomalous container behaviour, unexpected process execution, lateral movement — is the operational complement to build-time controls. DevSecOps secures the delivery pipeline; SecOps monitors what runs in production. Falco and eBPF-based tools feed alerts into SIEM and SOAR platforms.

- **[Incident Management and Business Continuity Planning (13)](13.%20Incident%20Management%20and%20Business%20Continuity%20Planning.md):** Immutable infrastructure and blue-green deployments enable rapid rollback. Pipeline artefact signing and SLSA provenance records support forensic investigation — what was running, from which source commit, by which pipeline run, on which build agent.

- **[Vendor Management (5)](05.%20Vendor%20Management.md):** Suppliers delivering software should be assessed on DevSecOps maturity. SBOM delivery, SSDF attestation (for US government supply chains), and SLSA provenance levels are increasingly expressed as contract requirements. The EU CRA makes supply chain security obligations legally binding for products sold in the EU. Under PSPF 2025 and SOCI CIRMP rules, Australian government entities and critical infrastructure operators must assess and manage software supply chain risk from their vendors — including FOCI risk in ICT procurement — which means supplier DevSecOps maturity, component provenance, and SBOM availability are now procurement evaluation criteria, not just best practice.

- **[Cyber Governance and Management (1)](01.%20Cyber%20Governance%20and%20Management.md):** DevSecOps policy — mandatory gates, valid exceptions, pipeline bypass approvals, shadow pipeline governance — must be formally governed. Unmanaged pipelines are a governance gap that auditors and regulators increasingly examine.

- **[Legal, Regulatory, and Compliance (3)](03.%20Legal,%20Regulatory,%20and%20Compliance.md):** US EO 14028 mandates SSDF attestation for US federal software vendors. The EU Cyber Resilience Act (Regulation EU 2024/2847, in force December 2024, fully enforceable December 2027) mandates SBOM, 24-hour vulnerability disclosure to ENISA, and secure-by-design development for products with digital elements sold in the EU — with fines up to €15 million or 2.5% of global annual turnover. In Australia, PSPF 2025 mandates technology lifecycle security, Essential Eight at ML2, and FOCI risk assessment in ICT procurement for all Commonwealth entities and their supply chains. SOCI Act CIRMP rules require critical infrastructure entities to address software supply chain as an explicit hazard domain and align to a recognised cyber framework. Compliance is increasingly verified through pipeline-generated evidence — SBOM records, provenance attestations, audit logs — rather than self-assessment documents.

- **[Cyber Architecture (17)](17.%20Cyber%20Architecture.md):** Zero trust principles — verify explicitly, use least privilege, assume breach — apply directly to pipeline design. Build agents, registry access, deployment credentials, and runtime environments should all be untrusted by default and verified before use.

- **[Cyber Culture and Education (18)](18.%20Cyber%20Culture%20and%20Education.md):** Security champions, developer security training, and blameless post-mortems are cultural capabilities that determine whether DevSecOps tooling is used effectively. The 2024 DORA research confirmed that transformational leadership and stable organisational priorities are stronger predictors of delivery performance than technology choices alone. Tooling without culture produces security theatre.

- **[LLM Security (19)](19.%20LLM%20Security.md):** AI coding assistants (GitHub Copilot, Cursor, Amazon CodeWhisperer) introduce new supply chain risks — generated code may contain vulnerable patterns, deprecated API calls, or hallucinated package names that resolve to malicious packages. AI-generated code requires the same SAST, SCA, and peer review as human-written code. The pipeline must not be relaxed for AI output.

## Australian Compliance Context

_Full regulatory detail is in [note 03](03.%20Legal,%20Regulatory,%20and%20Compliance.md). Volatile figures are in [note 00](00.%20Current%20Versions%20and%20Facts.md)._


DevSecOps does not exist in a regulatory vacuum in Australia. Three overlapping frameworks create concrete obligations that map directly onto pipeline design, software supply chain practices, and technology procurement.

### PSPF 2025 — Protective Security Policy Framework

The PSPF (July 2025 release, Department of Home Affairs) is mandatory for non-corporate Commonwealth entities and, in practice, extends to contractors and suppliers handling Commonwealth data. The Technology domain is the most directly relevant to DevSecOps, covering:

**Technology Asset Stocktake:** PSPF Direction 002-2024 required all Commonwealth entities to conduct a stocktake of all internet-facing systems and services by June 2025, capturing all manufacturers, suppliers, and providers of hardware, software, platforms, mobile applications, and as-a-service offerings that store, process, transmit, or transform official information. For DevSecOps teams, this means CI/CD tooling, build platforms, container registries, package repositories, and cloud environments are all in scope and must be inventoried. An SBOM for each production system directly supports this obligation.

**FOCI Risk in Procurement:** PSPF Direction 001-2024 requires entities to identify and manage foreign ownership, control, or influence (FOCI) risk when procuring and maintaining technology assets. For DevSecOps, this extends to the origin of build tooling, pipeline platforms, container base images, and open-source dependencies. The supply chain provenance controls that DevSecOps implements — SBOM generation, SLSA provenance, signed images — are the technical mechanism for demonstrating FOCI due diligence.

**ISM and Essential Eight Alignment:** PSPF 2025 requires entities to implement a cybersecurity strategy aligned with the ISM and to embed a Zero Trust Culture. The minimum Essential Eight maturity is ML2. The following Essential Eight strategies map directly to DevSecOps controls:

```
Essential Eight Strategy    DevSecOps Implementation
──────────────────────────  ─────────────────────────────────────────────────────
Application Control         Pipeline gates enforce signed, approved artefacts only.
                            Container admission policies (OPA/Gatekeeper) block
                            unsigned or unapproved images from running in production.

Patch Applications          SCA in the pipeline detects vulnerable dependencies.
                            Immutable infrastructure ensures patched images replace
                            old ones rather than patching running containers.
                            ISM requires critical patches within 48 hours; pipeline
                            SCA alerts must feed into remediation workflows with
                            tracked SLAs matching these timeframes.

Restrict Admin Privileges   Pipeline service accounts follow least privilege.
                            Separate credentials for build, staging, and production.
                            No developer has direct production access; changes go
                            through the pipeline.

MFA                         Access to CI/CD platforms, source repositories,
                            container registries, and secrets management must
                            enforce MFA, with phishing-resistant MFA (FIDO2)
                            required at ML2 and above.
```

**ASD Cyber Security Partnership Program:** PSPF 2025 requires participation in the ASD's Cyber Security Partnership Program, including connection to the ASD's Cyber Threat Intelligence Sharing platform. Threat intelligence feeds from ASD inform vulnerability prioritisation in DevSecOps pipelines — a CVE flagged as actively exploited by ASD warrants faster pipeline-enforced remediation than the standard CVSS-based triage.

**IRAP-Assessed Cloud and Hosting:** Systems processing OFFICIAL: Sensitive or classified information must use IRAP-assessed cloud services and comply with the Hosting Certification Framework. DevSecOps build and deployment pipelines running on cloud platforms must validate that those platforms hold current IRAP assessment status. This is a procurement and architecture consideration that constrains which cloud CI/CD and container services can be used for government workloads.

### SOCI Act 2018 and CIRMP

The Security of Critical Infrastructure Act 2018 (with amendments in 2021, 2022, and 2024) applies to responsible entities for critical infrastructure assets across 11 sectors (communications, data storage and processing, defence industry, energy, financial services, food and grocery, health, higher education, space technology, transport, and water). This covers a large proportion of Australia's significant private-sector organisations, not just government.

**Critical Infrastructure Risk Management Program (CIRMP):** Responsible entities must maintain a written CIRMP that identifies and manages material risks across four hazard domains:

```
CIRMP Hazard Domain          DevSecOps Relevance
───────────────────────────  ──────────────────────────────────────────────────────
Cyber and information        The primary domain. Entities must align to one of five
security                     prescribed frameworks by August 2024: Essential Eight,
                             NIST CSF, C2M2, ISO 27001, or AESCSF. DevSecOps
                             controls — SAST, DAST, SCA, pipeline gates, secrets
                             management, immutable infrastructure — are the technical
                             implementation of whichever framework is adopted.

Supply chain                 Entities must identify IT and OT supplier dependencies,
                             embed security requirements in contracts, conduct
                             periodic supplier reviews, and require suppliers to
                             report vulnerabilities. SBOM generation, SLSA provenance,
                             and vendor DevSecOps maturity assessment directly address
                             this domain. Responsible entities cannot assume their
                             software vendors have adequate supply chain controls
                             without evidence.

Personnel                    Access controls in CI/CD systems, least-privilege
                             pipeline accounts, and audit trails of who approved
                             what change are relevant to insider threat controls
                             required under this domain.

Physical security /          Out of direct scope for software pipelines but relevant
natural hazards              to the physical hosting of build infrastructure.
```

**Board Reporting:** Annual CIRMP reports must be approved by the board and submitted to CISC within 90 days of the end of the financial year (first due September 2024, annually thereafter). This means DevSecOps metrics, pipeline security posture, and supply chain risk assessments must be reportable at board level — not just to technical teams.

**Cyber Framework Selection:** Entities that adopt the Essential Eight as their CIRMP cyber framework inherit all the DevSecOps implications described under PSPF above. Entities that adopt NIST CSF align their pipeline controls to the Govern, Identify, Protect, Detect, Respond, Recover functions — with CI/CD security controls mapping primarily to Protect and supply chain risk management mapping to GV.SC (Govern function, supply chain risk).

### Australian Cyber Security Strategy 2023–2030

The Strategy's goal of making Australia one of the world's most cyber-secure nations by 2030 is implemented through PSPF updates, SOCI obligations, and the ASD's uplift programs. For DevSecOps practitioners, the practical implications are:

- Software supply chain security is explicitly a government priority. SBOM, provenance, and vendor attestation are moving from best practice to regulatory expectation.
- The Essential Eight is the minimum baseline for government, and is increasingly referenced in government contracts with private sector suppliers.
- Mandatory cyber incident reporting under both PSPF (significant incidents) and SOCI (within 12 hours for incidents with a significant impact on critical infrastructure) creates a direct dependency on runtime monitoring capabilities that DevSecOps programmes should feed.
